# Часть 1. Ответы на теоретические вопросы

Примеры написаны для PostgreSQL, там где Oracle и MS SQL Server ведут себя иначе, это указано.

## 1. Базовые понятия

### 1.1 Что такое СУБД и зачем она нужна, почему не хранить все в Excel или файлах?

СУБД это программа, которая хранит данные и управляет доступом к ним. Файлы и Excel не подходят, потому что не дают вот этого.

1) одновременная работа многих пользователей без потери изменений (блокировки, транзакции).
2) целостность. Типы, ограничения NOT NULL, UNIQUE, CHECK, внешние ключи не дают записать мусор.
3) объем и скорость. Индексы и оптимизатор находят нужные строки среди миллионов без чтения всего файла.
4) надежность. Журнал транзакций (WAL в PostgreSQL, redo log в Oracle) позволяет восстановиться после сбоя, есть бэкапы и репликация.
5) права доступа на уровне таблиц, строк и столбцов.
6) единый язык запросов SQL.

### 1.2 Какие СУБД знаешь, как их можно классифицировать?

- По модели данных. Реляционные (Oracle, MS SQL Server, PostgreSQL, MySQL). Документные (MongoDB). Ключ-значение (Redis). Колоночные аналитические (ClickHouse). Графовые (Neo4j). Временных рядов (InfluxDB).
- По нагрузке. OLTP для множества коротких транзакций (банковские операции) и OLAP для тяжелой аналитики по большим объемам.
- По хранению. Строковые и колоночные, дисковые и in-memory.
- По архитектуре. Встроенные (SQLite), клиент-серверные, распределенные.
- По лицензии. Коммерческие (Oracle, MS SQL) и открытые (PostgreSQL, MySQL).

### 1.3 Что такое реляционная модель?

Данные лежат в отношениях, то есть таблицах. Строка это кортеж, столбец это атрибут с типом (доменом). Каждая строка однозначно определяется ключом, связи между таблицами строятся через значения ключей. Порядок строк не определен, пока его не задать через ORDER BY. Работа с данными описывается реляционной алгеброй (выборка, проекция, соединение, объединение), SQL на ней основан.

## 2. Ключи и связи

### 2.1 Чем первичный ключ отличается от внешнего?

- Первичный ключ (PRIMARY KEY) однозначно определяет строку в своей таблице. Он уникален, не бывает NULL, в таблице он один (но может состоять из нескольких столбцов). Под него автоматически создается уникальный индекс.
- Внешний ключ (FOREIGN KEY) это столбец, который ссылается на первичный или уникальный ключ другой таблицы. Он гарантирует, что ссылка ведет на существующую строку. Может быть NULL, может повторяться. В схеме из задания `accounts.client_id` это внешний ключ на `clients.client_id`. Можно задать поведение при удалении родителя: ON DELETE CASCADE / SET NULL / RESTRICT.
- Ключ бывает естественным (ИНН, номер счета) и суррогатным (автоинкремент, uuid), а еще составным из нескольких столбцов.

### 2.2 Какие бывают типы связей? Как реализовать «многие ко многим»?

- Один к одному. Клиент и его паспортные данные. Внешний ключ с ограничением UNIQUE.
- Один ко многим. Клиент и счета. Внешний ключ на стороне «многих» (`accounts.client_id`).
- Многие ко многим. Счет может иметь нескольких владельцев, у клиента несколько счетов. Реализуется через промежуточную таблицу:

```sql
create table account_owners (
    account_id integer references accounts (account_id),
    client_id  integer references clients (client_id),
    role       text,               -- владелец, доверенное лицо
    primary key (account_id, client_id)
);
```

## 3. Нормализация

### 3.1 Что такое нормализация и зачем она нужна?

Нормализация это разбиение данных на таблицы так, чтобы каждый факт хранился в одном месте. Это убирает избыточность и аномалии вставки, обновления и удаления. Например, если город клиента записан в каждой транзакции, при переезде его придется менять в тысячах строк, и одна пропущенная строка уже даст противоречие.

- 1НФ. Значения атомарны, нет повторяющихся групп (нельзя хранить «RUB, USD» в одной ячейке).
- 2НФ. 1НФ и каждый неключевой атрибут зависит от всего составного ключа, а не от его части.
- 3НФ. 2НФ и нет транзитивных зависимостей, то есть неключевые атрибуты не зависят друг от друга (город клиента лежит в `clients`, а не в `accounts`).
- Есть и более строгие формы, но на практике обычно хватает 3НФ.

### 3.2 Когда денормализация оправдана?

Когда чтение важнее записи и соединения становятся слишком дорогими.

- аналитические хранилища и витрины, схема «звезда» и «снежинка»;
- отчеты по большим объемам, где заранее посчитанные агрегаты (остаток на счете, сумма за день) экономят минуты на каждом запросе;
- исторические снимки, когда нужно значение на момент операции (курс валюты на дату транзакции);
- кэширующие поля и материализованные представления.

Минус в том, что согласованность потом приходится поддерживать самим, триггерами, ETL или пересчетом.

## 4. SQL и работа СУБД

### 4.1 Чем WHERE отличается от HAVING?

WHERE фильтрует строки до группировки и не может использовать агрегаты. HAVING фильтрует группы после GROUP BY и работает с агрегатами. Логически запрос выполняется в порядке FROM и JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT, поэтому условия на обычные столбцы лучше писать в WHERE, так меньше строк попадет в группировку.

```sql
select client_id, count(*) from accounts
where closed_at is null          -- строки
group by client_id
having count(*) > 2;             -- группы
```

### 4.2 Какие виды JOIN знаешь?

- INNER JOIN. Только строки, у которых нашлась пара в обеих таблицах.
- LEFT (OUTER) JOIN. Все строки левой таблицы, справа NULL, если пары нет.
- RIGHT JOIN. Зеркально LEFT.
- FULL OUTER JOIN. Все строки обеих таблиц.
- CROSS JOIN. Декартово произведение, каждая строка с каждой.
- SELF JOIN. Таблица соединяется сама с собой (сотрудник и руководитель).
- Полусоединение и анти-соединение через EXISTS и NOT EXISTS.
- LATERAL в PostgreSQL, CROSS APPLY и OUTER APPLY в MS SQL и Oracle, в старом Oracle внешнее соединение писали через `(+)`.

Если после LEFT JOIN поставить условие на правую таблицу в WHERE, он фактически становится INNER JOIN, поэтому такие условия пишу в ON.

### 4.3 Чем DELETE, TRUNCATE и DROP отличаются?

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| Что удаляет | строки, можно с WHERE | все строки | таблицу целиком со структурой, индексами и правами |
| Тип команды | DML | DDL | DDL |
| Триггеры на удаление строк | срабатывают | нет | нет |
| Скорость | построчно, пишет журнал по каждой строке | быстро, освобождает страницы целиком | быстро |
| Счетчики identity | не сбрасывает | сбрасывает (MS SQL всегда, PostgreSQL с RESTART IDENTITY) | исчезают вместе с таблицей |
| Откат | да | в PostgreSQL и MS SQL внутри транзакции да, в Oracle нет (неявный COMMIT) | в PostgreSQL и MS SQL в транзакции да, в Oracle нет, но есть корзина FLASHBACK TABLE |

Еще TRUNCATE нельзя применить к таблице, на которую ссылаются внешние ключи (в PostgreSQL можно с CASCADE).

### 5.1 Что такое NULL и как с ним работать?

NULL означает «значение неизвестно или отсутствует», это не ноль и не пустая строка. Логика становится трехзначной (TRUE, FALSE, UNKNOWN).
- Любое сравнение с NULL дает UNKNOWN, поэтому `x = null` не работает. Нужны `is null` и `is not null`, в PostgreSQL еще `is distinct from`.
- Агрегаты (SUM, AVG, COUNT(col)) пропускают NULL, а COUNT(*) считает все строки.
- Замена значения через COALESCE (стандарт), NVL в Oracle, ISNULL в MS SQL. NULLIF(a, b) возвращает NULL, если a = b, это удобно против деления на ноль.
- Если в подзапросе есть хоть один NULL, `x not in (подзапрос)` не вернет ни одной строки, поэтому для анти-соединения лучше NOT EXISTS.
- В Oracle пустая строка равна NULL.
- В GROUP BY и DISTINCT все NULL попадают в одну группу. UNIQUE обычно допускает несколько NULL (в MS SQL только один).

### 5.2 Что такое индекс, есть ли у него минусы?

Индекс это отдельная структура (чаще всего B-дерево), которая позволяет найти строки по значению столбца без чтения всей таблицы. Бывают B-tree, hash, bitmap (Oracle), GIN и GiST (PostgreSQL), кластерные и некластерные (MS SQL), составные, частичные, покрывающие (INCLUDE).

Минусы у индексов есть.
1) замедляют INSERT, UPDATE и DELETE, ведь каждый индекс тоже надо обновить;
2) занимают место на диске и в памяти;
3) бесполезны при низкой селективности (столбец пол, флаг), там оптимизатор все равно прочитает таблицу;
4) не используются, если на столбец навесили функцию (`where extract(year from registered_at) = 2025`), нужен индекс по выражению или условие диапазоном;
5) составной индекс работает по левому префиксу, порядок столбцов важен;
6) требуют обслуживания (фрагментация, перестроение, статистика).

Проверить, использует ли запрос индекс, можно через EXPLAIN (ANALYZE) в PostgreSQL, EXPLAIN PLAN в Oracle и план выполнения в MS SQL.

### 5.3 Что такое транзакция?

Это группа операций, которая выполняется целиком или не выполняется вовсе. Например, перевод между счетами, где списание и зачисление должны пройти вместе.

```sql
begin;
insert into transactions values (17, 101, now(), 1000, 'out');
insert into transactions values (18, 104, now(), 1000, 'in');
commit;   -- при ошибке rollback, и не будет ни одной из двух записей
```

Свойства ACID.
- Atomicity (атомарность). Все или ничего.
- Consistency (согласованность). После транзакции все ограничения выполняются.
- Isolation (изолированность). Параллельные транзакции не мешают друг другу.
- Durability (долговечность). После COMMIT данные переживут сбой.

Уровни изоляции и аномалии, от которых они защищают.

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможны |
| READ COMMITTED | нет | возможно | возможны |
| REPEATABLE READ | нет | нет | возможны по стандарту |
| SERIALIZABLE | нет | нет | нет |

По умолчанию в PostgreSQL, Oracle и MS SQL стоит READ COMMITTED. Внутри транзакции можно поставить SAVEPOINT и откатиться только до него. При взаимной блокировке (deadlock) СУБД сама откатывает одну из транзакций. В Oracle DDL-команды делают неявный COMMIT, а в PostgreSQL DDL можно откатить вместе с транзакцией.
